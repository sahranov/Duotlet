# Выпуск обновлений Duotlet

Репозиторий: https://github.com/sahranov/Duotlet

Пользователь получает окно с новой версией и кнопками «Скачать», «Позже» и
«Пропустить версию». Скачивание открывается в браузере. После скачивания нужно
закрыть Duotlet и заменить приложение в папке «Программы».

Автоматическая проверка включена по умолчанию и выполняется не чаще раза в сутки,
пока приложение запущено. Её можно отключить в настройках. Ручная проверка
доступна в настройках и меню, даже для ранее пропущенной версии. Ошибки фоновой
проверки не открывают окна. Неудачная проверка не означает, что версия последняя.

## Экспериментальный выпуск без Apple Developer

2026-09-18 пользователь явно разрешил публикацию экспериментальной ad-hoc сборки.
Стабильный сценарий `.github/workflows/release.yml` по-прежнему требует Developer ID;
экспериментальный выпуск не является автоматическим запасным вариантом.

```sh
bash scripts/package-experimental.sh
```

Сценарий собирает универсальный SwiftPM-вариант без расширения Control Center и
App Group, проверяет обе архитектуры и подпись, создаёт DMG, ZIP и SHA256SUMS.txt
в `output/experimental/0.2.0/`, затем удаляет временный `.app`. Ничего не устанавливает
и не запускает. Существующие архивы не перезаписываются.

Для первого такого выпуска используйте тег `v0.2.0-experimental.1` и обязательно
включите **Set as a pre-release** в GitHub. Загрузите оба архива и контрольные суммы
до публикации. Описание должно начинаться с прямых ссылок DMG/ZIP и явно сообщать
об отсутствии подписи Apple, нотарификации и Control Center. Инструкция первого
запуска и ограничения находятся в `EXPERIMENTAL.md`. Стабильная проверка обновлений
не предлагает prerelease пользователям.

Разрешение распространяется только на публикацию архивов. Установленную
`/Applications/Duotlet.app`, TCC и проверки преемственности подписи не менять.

## Первый стабильный релиз

Сначала настройте подпись из раздела ниже. Сценарий публикации намеренно
останавливается без неё: ad-hoc замена приложения нарушает сохранение
разрешений записи экрана. Это ограничение выпуска, а не проверки обновлений.

После настройки подписи и загрузки кода в main отправьте тег текущей версии:

```sh
git tag v0.2.0
git push origin v0.2.0
```

В GitHub → Actions → Release начнётся сборка. Сценарий проверит версию, соберёт
универсальное приложение для Apple Silicon и Intel, подготовит DMG и ZIP и
загрузит их в черновик релиза. Только после загрузки обоих файлов релиз станет
публичным и будет доступен проверке обновлений.

До первого релиза приложение сообщает «Обновлений пока нет».

## Следующие версии

1. Измените приложение и проверьте его работу.
2. Выполните `python3 scripts/prepare-release.py 0.3.0`. Скрипт обновляет версии
   приложения, расширения и проекта Xcode, но ничего не отправляет в GitHub.
3. Обновите `RELEASE_NOTES.md`: номер версии и список изменений.
4. Зафиксируйте проверенные изменения и отправьте main и тег:

```sh
git add Sources Resources Tests scripts Duotlet.xcodeproj Package.swift Package.resolved README.md RELEASING.md RELEASE_NOTES.md .github build.sh .gitignore
git commit -m "Release 0.3.0"
git push origin main
git tag v0.3.0
git push origin v0.3.0
```

Используйте новый, возрастающий номер `X.Y.Z` для каждого выпуска. Опубликованные
релизы не перезаписываются. Если нашли ошибку, выпустите следующую версию.
Обычный push в main не выпускает обновление. Не помечайте релиз как prerelease:
такие версии пользователям не предлагаются.

Названия файлов важны: `Duotlet-0.3.0.dmg` и `Duotlet-0.3.0.zip`. Проверка
принимает только готовые файлы из соответствующего релиза этого репозитория.
Отдельный сервер, API-токен в приложении и App Store не нужны.

## Без Apple Developer

Проверка обновлений, окно с новой версией и скачивание с GitHub не требуют
Apple Developer. Локально можно собрать приложение для проверки компиляции.
Автоматическая публикация релизов пока заблокирована защитой постоянной подписи.
У ad-hoc сборок меняется идентичность подписи; сохранение ранее выданных
разрешений записи экрана при замене приложения не гарантируется. Для обычных
обновлений с сохранением разрешений нужна постоянная Apple-подпись.
Не устанавливайте локальные ad-hoc сборки поверх уже авторизованного приложения.
Проверка обновлений сама не меняет приложение, защиту macOS или разрешения.

Расширение Control Center требует правильно подписанного App Group. В ad-hoc
сборке его работу не обещаем; управление через меню остаётся доступно.

## Подпись Для Публикации

Для Developer ID и нотарификации добавьте в GitHub → Settings → Secrets and
variables → Actions следующие Secrets:

- `APPLE_CERTIFICATE_P12_BASE64`: сертификат Developer ID Application вместе с
  закрытым ключом, экспортированный в P12 и закодированный в base64.
- `APPLE_CERTIFICATE_PASSWORD`: пароль этого P12.
- `APPLE_TEAM_ID`: Team ID.
- `APPLE_NOTARY_KEY_P8_BASE64`: ключ App Store Connect API в base64.
- `APPLE_NOTARY_KEY_ID`: ID этого ключа.
- `APPLE_NOTARY_ISSUER_ID`: Issuer ID.

Добавьте Variable `DEVELOPER_ID_ENABLED` со значением `true`. Следующий релиз
будет подписан и отправлен на проверку Apple. При ошибке подписи или проверки
релиз не публикуется. Закрытые ключи не должны попадать в репозиторий.
